Why I want to work on memory

Kumudini Gandesiri, November 2026

My job is getting PCIe links up on new ASIC platforms. Nothing in that description says memory. But two of my personal projects are about DRAM, and a third analyzes wafer defect maps. When your free-time work keeps pointing in one direction, it's worth asking why.

The question I keep asking

The answer I've landed on is margin. In hardware validation, "does it work?" is only the first question. The more useful one is "how close is it to not working?"

At AMD, I analyze link training data and Linux logs to find the root cause of marginal links and errors. At Apple, I monitored test parameters with control limits, Cpk, and SPC charts to flag anything drifting toward a spec limit. In both jobs, the interesting failures were the ones that hadn't fully happened yet.

That's also why I built my DRAM Timing Margin Analyzer. It takes setup and hold sweep data, calculates the margin at each point, and flags results within 15% of the spec limit across voltage corners. A pass/fail answer would have been simpler to produce, but it would have hidden the most useful information.

Why memory fits that question

Memory makes margin hard to ignore. A NAND cell stores data as a threshold voltage, so a digital bit depends on an analog value staying within range. As I've read more about it, I've found that much of what happens inside an SSD exists to keep that range under control across wear, time, and heavy use.

An SSD also brings together many things I already enjoy working with: a PCIe link, a controller, firmware, DRAM on many designs, and a large amount of test data. I'd like to learn how those pieces behave together as one product.

Why applications engineering

The part of my work I find most satisfying is turning a messy pile of logs and measurements into an explanation other people can act on. Applications engineering is built around that same skill: understanding the technical detail, then making it clear to the customers and teams who depend on it.

I'm also interested in how AI can help with this work. My DRAM Spec-Limit Screening Agent, built with Google Cloud Generative AI, screens open-source DDR2 to DDR5 benchmark data against spec limits and reports pass rates. I'd like to apply that kind of tool to technical analysis and knowledge sharing.

What I still need to learn

I haven't worked on NAND or SSD products yet. I'm starting from adjacent experience, and I want to be clear about that. Next on my list is a hands-on NVMe test on Linux, using fio and nvme-cli, and writing up the results like an application note.

In the meantime, I've written up how my PCIe debug habits apply to what I'm learning about NAND.
